                                              Android App Modularization

Q1

Modularization means splitting a codebase into independent parts called modules, where each piece has its own clear purpose. It solves the growing codebase problem by breaking one huge project into smaller pieces, so changing one part does not break unrelated code.

Q2
Too fine grained means creating way too many tiny modules. A downside is that it adds too much boilerplate and build complexity that becomes hard to maintain.
Too coarse grained means keeping modules too big. A downside is that you basically end up with another monolith and lose the real benefits of modularity.

Q3

Low coupling means modules are independent so changing one does not break the other. High cohesion means all code inside a module works together on the same domain or job.

For the two feature modules that know too much about each other, they should be combined into one module. For the mixed book and payment code, they should be split into two separate modules because they belong to completely different domains.

Q4

The three primary responsibilities are encapsulating all data and business logic of a domain, exposing the repository as a public API, and hiding implementation details and data sources from the outside.

To hide data sources from outside the module, you use the private or internal visibility keywords in Kotlin.

Q5

A feature module is an independent part of the app that usually represents a screen or a group of related screens, like a flow. It typically contains the UI and a ViewModel to manage state and screen logic. Feature modules depend on data modules.

Q6

The mediator pattern uses a third module to pass messages and data between two modules so they do not connect to each other directly. The app module usually plays this role because it owns the navigation graph.

The navigation line from the lecture is:
navController.navigate("checkout/$bookId")

Q7

Dependency inversion makes this possible because other modules only depend on the abstraction module with the interface, not the actual database code. So if you switch from Room to Firestore, you only have to change the implementation module, and other modules do not need to change at all.

Two benefits from the lecture are decoupling and interchangeability.

Q8

Using implementation is better because api exposes internal dependencies to other modules. With implementation, you hide those extra details and Gradle does not have to rebuild as many modules, which saves build time.

A version catalog is a central, type safe file in Gradle where you list all your dependencies and their versions in one place for the whole project.


                                        Build Logic, Convention Plugins & Gradle

Q9

The three problems are Duplication, Drift, and Friction.

Build logic is the code and configuration that defines how the project is built.

Q10

build.gradle.kts handles the build setup for a single module.

settings.gradle.kts manages the overall project structure and the plugin and dependency setup.

gradle.properties holds properties for Gradle itself and project wide settings.

Q11

Three problems of the monolith are that one app module has too many responsibilities, a small change can invalidate large parts of the build, and multiple teams end up working inside the same files.

The three recommended module types are:
The app module, which is the entry point that brings the app together.
Feature modules, which handle the UI and logic for specific features.
Core modules, which hold reusable shared tools like networking or database code.

Q12

A convention plugin is a reusable build recipe for a group of modules so you do not have to repeat the same setup everywhere.

Apply means the module only needs to add that one single plugin.
Configure means the plugin automatically sets up the shared Android and Kotlin settings for it.
Customize means the module only keeps the choices and dependencies that are unique to itself.

Minimal build.gradle.kts from the lecture:

plugins {
id("company.android.feature")
}
dependencies {
implementation(project(":core:ui"))
implementation(project(":core:domain"))
}

code from the lecture:

class AndroidFeatureConventionPlugin : Plugin {
override fun apply(project: Project) {
project.pluginManager.apply("com.android.library")
project.pluginManager.apply("org.jetbrains.kotlin.android")
project.extensions.configure {
// shared Android configuration
}
}
}
